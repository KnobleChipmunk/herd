### U1 — capability inventory and bounded readiness checks: 5/5

Detect known harness executables and versions through supported adapters, selected transport availability, and explicitly configured providers/endpoints and profile references. No filesystem-wide credential hunt, network/port scan, automatic install, model download, server startup or login. User-specified executable locations remain possible. Treat a found unknown harness as detected-but-unsupported, not launch-ready.

Report independent facts: executable present, adapter/version supported, authentication requirement and status, configured model candidates, required tools/permissions, and latest invocation result with timestamp. Authentication can be **not required** for a local provider; a model catalog is not entitlement. Distinguish needs-login, model-denied, rate-limited, unreachable, unsupported and unknown instead of flattening them into “unavailable.” A timeout is not evidence that an account lacks access.

Optional active checks require approval or saved probe policy because they consume resources. Probe only selected candidates using the exact harness/provider/endpoint/auth-profile/model/settings tuple intended for launch, a synthetic prompt with no project content, restricted tools and a disposable non-project working directory. Cache sanitized observations by that tuple and CLI version; recheck when identity/configuration changes or evidence expires/fails. A successful probe means “this invocation worked then,” not “this model is good at QA.” At dispatch verify the actual runtime/model where supported; unresolved aliases stay explicitly unresolved. Never ask the model to identify itself as proof.

### U2 — explicit configuration and assisted discovery: 5/5

Provide manual and assisted modes plus read-only validation; names are design concepts, not existing commands. Manual mode accepts supplied bindings without forcing broad discovery. Assisted mode inventories supported candidates, asks which profiles the user permits, recommends role assignments, shows gaps/diversity/budget implications, and previews the effective configuration before saving. Existing selections remain authoritative; detecting another installation must not silently replace them.

For a Claude-only machine, prompt: “Claude Code is configured. Choose the available model for lead/design, builder, and independent review/QA; use different suitable models where possible. May setup verify these choices with bounded requests?” Allow explicit model entry when enumeration is unavailable, marking it unverified. If only one candidate can be used, offer separate fresh-context role sessions with a visible diversity limitation, or human review/additional setup. Do not insist on installing another vendor. Noninteractive mode uses saved policy and returns actionable unresolved requirements rather than hanging on prompts or choosing an expensive/cloud fallback. Setup does not start the team.

### U3 — portable policy, local bindings, immutable run resolution: 5/5

| Layer | Proposed home | Contents |
|---|---|---|
| Portable project policy | Versioned `herd.yaml` and role cards in the repository | Role/workflow contracts, capability requirements, author/evaluator exclusions, preferred diversity, allowed fallback policy, resource limits and logical profile names; relative artifact references. No user-specific account, executable or endpoint assumptions. |
| Machine-local configuration | OS-appropriate per-user herd config; optional ignored project override | Concrete harness/provider/model choices, executable and endpoint locations, approved auth/profile references, transport, notification target references and concurrency limits. Store secret references, not secret values or copied token caches. |
| Run evidence | Existing git-common-dir herd run storage | Resolved role → binding → session/candidate mapping, configuration/schema version, sanitized readiness evidence, selected fallback and reason. No credentials. Re-resolution on another machine creates a new record, not rewritten history. |

Use explicit precedence for binding values: invocation override → ignored project-local override → user-local profile → portable defaults. These layers cannot relax portable hard requirements or organizational restrictions; report incompatible overrides. Discovery produces suggestions, not a higher-priority config layer. Validate schema versions and reject unknown/misspelled fields; offer explicit migrations and preview rather than silently modifying configuration. Hardware capacities, accounts and absolute paths do not travel with the project. Workflow records and Markdown evidence do; native session resume and login portability are separate capabilities, never guaranteed by copying YAML.

### U4 — one harness and even one model are supported configurations: 5/5

Make roles harness-neutral, including lead, builder, QA, designer and librarian. Claude-only and Codex-only retain the same role contracts and independent evaluation; local-only can qualify if its adapter and task capabilities actually satisfy them. Different model choices inside one harness count as model diversity; a second harness running the same model is not automatically a second model perspective. Different logins are not model diversity either.

Replace H's global “never Opus” rule with explicit policy: a selected independent evaluator cannot be the candidate's author/session; different suitable model identities are preferred, not universally required. The lead's pre-execution makes it an author too. Separate fresh sessions on the same model preserve evaluator separation but not model diversity; disclose that limitation. If a project expressly requires cross-model evaluation, do not bypass it—request a policy decision or an appropriate human review. Do not create fake independence by renaming a pane or assigning two hats in one context. A different vendor is not proof of statistically independent errors.

### U5 — role-specific recommendations with evidence, not brand stereotypes: 4/5

Recommend from the user's eligible pool. First satisfy tools, permissions, privacy, environment, model access and budget; then compare role-relevant observed quality and latency; then favor diversity across author/evaluator pairs among suitable choices. Examples of criteria: Architect/Planner—reasoning about constraints and long specifications; Builder—reliable edits/tool use and repository tests; Reviewer—independent defect discovery and low false positives; QA/Dogfood—ability to exercise the selected public surface, including browser/image capabilities when needed. These are task needs, not claims that any named model wins them.

Show the reason and evidence date for each suggestion: user preference, official capability documentation, or measured local task outcomes. Unknown specialty remains unknown. The current roster can ship as an explicitly labeled example profile, not universal defaults. Offer a separately authorized small calibration on representative tasks when evidence is lacking; do not make expensive benchmarking mandatory setup. Diversity should be encouraged at configuration time and reported when lost, but never outweigh hard suitability/privacy/cost constraints. No automatic model leaderboard or “Claude creative/Codex precise” assumption.

### U6 — explicit identity and bounded fallback policy: 5/5

A binding includes harness, provider, model, auth-profile reference, relevant settings and endpoint—not merely a model string. The lead's current session must satisfy its selected binding; setup cannot relabel it or change its login/model in place by declaration. Incompatible lead settings require a new compatible session or an explicit plan adjustment.

Keep fallback lists ordered, finite, cycle-checked and limited to operator-approved bindings. A fallback cannot silently change billing source, organization, data destination, permissions, independence requirements or resource limits. Distinguish transient backoff from permanent rejection; do not exhaust every model/account on a rate limit. Account/profile selection is a user decision, not license to rotate accounts to evade limits. Use provider-supported per-session isolation where verified; otherwise report the multi-login combination unsupported rather than switching global credentials under active agents. CLI:350–386 confirms even OpenRig's profile metadata is not proof of a live account and profile switches need session restart. Official [OpenAI authentication documentation](https://learn.chatgpt.com/docs/auth) also distinguishes subscription/API access, their different policy/billing contexts, and local providers that need no authentication.

### U7 — real adapter seam and capability-conditioned prerequisites: 4/5

Centralize discovery, bounded probe and launch/observation translation behind a small adapter interface; HP's three command implementations already provide a real variation point. The same resolved binding must feed preflight, launch, role packets and monitor. Capture lifecycle/restore/usage capabilities explicitly; unsupported context metrics remain unknown, not guessed. Do not invent a generic provider protocol that makes every agent CLI interchangeable. Start with verified adapters for the existing harnesses; let opencode/Hermes and other combinations be declared candidates with explicit support status until their contracts are validated. An HTTP model endpoint is a provider, not by itself an agent harness with editing, tools and lifecycle control.

Derive prerequisites from the selected workflow and bindings, not HF's fixed global list: Claude-only must not require pi/Codex/local servers. Check browser/test tooling when selected QA needs it, GitHub tooling when using GitHub, and local endpoint/model/resource capacity when selected. Limit concurrency independently of role count: one model or GPU can run several roles sequentially. Expected resource waits are not stalls.

### U8 — non-model portability and acceptance matrix: 4/5

Document the support envelope explicitly. H:47–48 currently requires Herdr; model portability does not magically support every terminal/OS. Keep Herdr as the initial verified execution adapter while separating role policy from that transport. A missing supported transport gets an actionable setup limitation; building another transport is a separate decision informed by P, not hidden scope. Do not claim the full workflow works without it.

Other named blockers: host-specific shell quoting/paths and custom prompt file (H:163–200); blanket permission bypass in launch examples (H:185–195); hardcoded Python/pytest/ruff/mypy checks (H:370–372) rather than project commands; host-specific push credentials (H:324–330); Hermes/local-model librarian and personal vault paths (H:503–520; `tools/merge_stack.py:165–185`); UI/notification availability; skill/tool installation and harness-specific instruction loading. Bind the librarian to supported alternatives or mark a pending post-run obligation, rather than require local inference everywhere or silently lose learning. Preserve the human gates regardless of provider.

Acceptance should exercise the resolver/adapter interface with fixtures for Claude-only, Codex-only, mixed cloud/local, one model only, no usable candidates, stale auth, unsupported CLI, wrong endpoint/profile, rate limits and constrained concurrency. Add redaction, policy-override, fallback and configuration-migration tests. Separately authorized smoke runs verify supported real combinations; fake inventory tests are not proof that another harness works. P remains a 60-minute architectural evaluation, not a certification of all combinations.
