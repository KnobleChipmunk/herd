### What the sources change

The video is a useful division of responsibilities, not the sole possible topology. The shipped factory has planner, builder, QA, reviewer, dogfood, release, orchestrator; it has no separately named Architect seat (`S/rigs/launch/factory-rsi/rig.yaml:17–86`). Its inner order is plan → implement → QA → review → release; Dogfood is outside that loop against the shipped product (W:3–18,64–136). The source explicitly leaves the exact continuous Dogfood runtime mechanism to later refinement (W:16–18,57–60): the example is not proof of autonomous operation. The `openrig-architect` skill designs **agent rigs**, not product architecture (`../openrig-src/skills/_canonical/core/openrig-architect/SKILL.md:3,29–31`); the kernel advisor uses it for that purpose (`S/rigs/launch/kernel/agents/advisor/lead/guidance/role.md:3–16,28–31`). A role/agent/rig-file search found no separate product-Architect definition in those files; that does not disprove the video or a custom author rig.

OpenRig itself permits neighboring roles to share a seat unless independence is selected, and warns against inventing work for idle roles (`S/agents/orchestration/orchestrator/guidance/role.md:18–25`). Consequently, YAML needs responsibilities, activation conditions and authority boundaries, then bindings to sessions—not just a longer list of models.

### Architect — 4/5 for an explicit lead-held role; 2/5 for a permanent extra seat

**Covered:** the lead is strategist, spec author and dispute judge (H:245–268,536–543); D already distinguishes strategist from dispatch lead (D:13–14,31–39). Plan review independently challenges conventions and boundaries (H:216–228). **Gap:** an issue-local implementation plan is not an explicit owner of cross-ticket architecture: module boundaries, invariants, dependency sequencing, accepted tradeoffs and the effect of Dogfood findings on the design. **Shape:** name `architect` separately from `planner` in the role catalog but bind both to the existing Claude lead initially. At intake, and when cross-cutting findings arise, Architect supplies a bounded design decision with interfaces/invariants/non-goals and affected tickets; Planner turns that into executable tasks. Keep decisions in existing OpenSpec `design.md`, not a new competing design ledger. Plan reviewer (existing Codex assignment) challenges it; the lead retains pre-execution. An independent architectural consultation can use slot 3 for a named uncertainty, but it cannot silently change scope or replace the operator's product decisions (H:63–67,301–310). This makes architecture visible without claiming another permanent agent is already justified.

### Test QA — 4/5 for selected independent outcome verification

**Covered:** substantial testing already exists: lead pre-execution, builder full checks, reviewer touched tests and selected mutations (H:255–268,338–343,370–396,461–468); D:65–71 also names an end-to-end smoke. **Gap:** reproducing a verified implementation and its tests does not independently establish that a realistic public journey satisfies the user's contract. The plan reviewer already tackles shared faulty assumptions by reasoning; QA adds execution of independently chosen scenarios, not another identical suite run. This matches OpenRig's contract: exercise the public journey, report untested cases, and do not let an author count as independent QA (`S/agents/development/qa/guidance/role.md:18–23`).

**Shape:** select a QA assignment at planning for new user-facing journeys, risky integrations, migrations or material failure/recovery behavior; small changes can remain builder-verified with the reason recorded. Use a fresh Codex QA context in slot 3 after plan review has finished, bound to the existing build-review model profile initially; harness choice is a starting proposal, not an evidence-backed model ranking. This requires amending H:151,190–201, which currently reserve Codex in slot 3 for plan review. After the builder/reviewer pair is clean, QA executes the selected journey on an identified candidate before final lead signoff; it may run safely scoped fixture/scratch operations but cannot modify the candidate and still certify it independently. Output: candidate revision or tree fingerprint, environment, expected/observed results, reproduction/evidence, unchecked coverage, verdict. In-scope defects return to builder; after candidate changes, affected review and QA evidence must be renewed. Broader discoveries become separate tickets; inability to run is BLOCKED/NOT CHECKED, not PASS. Bound remediation under the existing lead escalation policy, not an additional unbounded QA ping-pong. No merge authority.

### Dogfood — 4/5 for a bounded, separately scheduled usage assignment

**Covered:** herd gathers workflow friction and retrospectives, and its librarian proposes improvements (H:344–357,503–520). That is learning from building, not independently using the shipped product. **Gap:** usability, defaults, installation/upgrade, long-running workflows and real operator friction can remain invisible even with clean code review and QA. The shipped role explicitly differentiates product use from pre-release QA (`S/agents/factory-rsi/dogfood/guidance/role.md:3–28`).

**Shape:** a Codex Dogfood assignment on a specifically identified released/installed build (or merged version only when that is what the user actually consumes), using approved test accounts/data and a real task. Start with a declared 20-minute session, defined stop conditions and evidence budget; do not silently install/update the user's live system. Reuse the specialist pane in a separate scheduled run; current H:358–368 shuts down build agents, so Dogfood must not depend on their survival. Output prioritized reproducible findings and the attempted journey, including useful friction that is not a code defect. Ticket them → lead triage → Architect/Planner; link duplicates and distinguish current-contract bugs from new product choices. Findings are not automatic permission to expand the current assignment (H:98–118,295–310). Keep human approval for new scope/cost/behavior and existing merge policy. This is not an inner build gate or a claim that continuous self-improvement is safe. Continuous always-on seat: 2/5 pending bounded trials and explicit authorization.

### Release manager — 2/5 for a separate seat; 4/5 for a release-preparation contract

**Covered:** lead final review, commit, push, PR creation and operator merge are explicit (H:314–337,545–569); D:73–77 describes an older, stricter arrangement. **Gap:** a release-oriented project can need version/compatibility checks, upgrade/rollback instructions and a coherent evidence-linked release summary beyond a PR. **Shape:** initially a `release_prep` hat on the Claude lead after selected reviews/QA, preparing notes/docs/PR and pointing to evidence on the exact candidate. Operator retains merge and any release/publish authority not already explicitly granted; do not copy OpenRig's absolute no-push rule over herd's existing branch-push policy. Its release role does prohibit publishing and holds a human signoff (`S/agents/factory-rsi/release-manager/guidance/role.md:18–33`; W:105–136). If recurring packaging work becomes substantial, trial a Claude preparation-only specialist in slot 3 with narrowly granted artifact writes; no independent gate or unattended shipping authority simply because it is called release manager.

### Orchestrator peer — 2/5 for a standing second controller

**Covered:** lead routes and rules; plan reviewer provides independent challenge, build reviewer checks implementation (H:216–228,245–248,311–319,386–396). **Gap:** a second perspective may catch missing work, dependency mistakes or falsely consolidated status across a large assignment, but current sources do not establish that a continuous co-orchestrator fixes a measured problem. The product-team sample really does give a Codex peer delegation edges to QA and a second reviewer (`S/rigs/preview/product-team/rig.yaml:13–22,63–78`), not merely advisory status. **Shape:** preserve one command authority and user-facing lead. For a multi-stream or contested plan, use the existing Codex plan-review slot for a bounded coordination audit: check scope/dependencies/coverage and return a file, without independently dispatching, cancelling or reprioritizing work. Expand plan-review scope explicitly when selected; don't smuggle this into its current brief. A true co-controller would need exclusive ownership partitions and conflict resolution first. Do not introduce it just because context usage is high; v2's evidence requirement for 7b remains.

### Other meaningful gaps — Product Designer and product-intake responsibility

**Product Designer: 3/5 as an on-demand Claude specialist, not a standing pane.** H:249–254 covers design documentation, but its role contract does not explicitly own interaction states, discoverability and coherent user flows. The shipped product-team includes this seat (`S/rigs/preview/product-team/rig.yaml:38–42`); its actual contract covers flows, copy, edge states and design coherence (`S/agents/design/product-designer/guidance/role.md:18–32`). Select it for UI/interaction ambiguity before the plan is frozen, in slot 3, producing a flow/state sketch and acceptance examples consumed by Planner and QA. New user-visible behavior still goes to the operator where H requires it. It may later assess the result, but cannot count as an independent evaluator of its own authored candidate.

**Product intake/PM: 4/5 as an explicit lead-held responsibility; 2/5 for a separate PM rig now.** The shipped `S/rigs/focused/pm-team/rig.yaml:4–8,14–22,35–38` distinguishes PM, researcher and prototype builder. Herd already picks priorities and asks product decisions (H:63–67,245–254), but Dogfood needs a named triage destination. Have the lead classify findings against current intent, rank proposed tickets with evidence, and consult the operator on new goals. Architect determines technical implications; Planner specifies approved work. A focused researcher can occupy slot 3 for a stated uncertainty, already supported by H:151,190–201; no new permanent research team is justified here. Librarian remains the workflow-learning owner, not a substitute for product-use feedback.

### Team shape and YAML consequences

Recommended default: existing lead, local pi builder, independent Codex build reviewer, and a reusable specialist slot. Architect/Planner/Orchestrator/release preparation are distinct hats currently bound to lead; plan review and selected QA occupy the specialist slot at different times. Dogfood is a separate bounded run. Preserve author/evaluator independence across roles: renaming a pane does not erase authorship or prior context. A constrained four-slot layout is an initial deployment choice, not a hard limit on the YAML model or monitor.

The role catalog should describe purpose, inputs, outputs, activation trigger, scope, evidence and authority. Assignment bindings resolve those roles to an agent session, runtime/model profile, candidate and allowed workspace/environment. Workflow declarations select required steps and return paths. Communication edges alone are not workflow routing (`S/rigs/launch/factory-rsi/rig.yaml:88–90`). Record why a conditional role was not selected; require named disposition for a selected gate that could not run. YAML constraints remain advisory until checked by tools, as v2 already says. Deterministic watchdog stays a service, not an agent with authority to invent work.

For the next design revision, put a **team responsibility/activation decision before implementing cards and YAML**. Preserve the existing recovery/attention/monitor priorities and P comparison; add role binding, shared-seat lifecycle and conditional independent QA to P's questions. Bounded QA/Dogfood trials can use existing evidence files and tickets before a custom queue is built; do not make role learning wait for every infrastructure row. No live trial is authorized by this discussion.

### Exact changes proposed to v2

**Row 3 — expand, retain 5/5.** Cards describe the complete responsibility map, not only today's pane names: Orchestrator, Architect, Planner, Builder, plan/build Review, selected QA, bounded Dogfood, release preparation, optional Product Designer, product intake and existing Librarian. An individual card can reference a shared contract; every role need not get a separate agent or a mandatory pipeline stage. Current-step packets include the chosen role, candidate/environment, required evidence, return route and independence requirement. The lead's architecture/planning work becomes visible work with outputs, not an unnamed black box.

**Row 4 — expand, retain 4/5.** Replace “define seats beyond the current four” with “define roles independently from seat/session bindings.” QA can share slot 3 over time; Dogfood can be its own later run; neither requires more than four concurrent panes initially. YAML also declares project capability requirements, activation/skip conditions, author/evaluator exclusions, allowed operations and time/cost limits. A resolved assignment records role + session + candidate + scope + selected checks. Model/runtime profile and fallback are bindings, not definitions of authority or guaranteed independence. Actual enforcement remains explicit; no invented OpenRig-compatible schema is being claimed.

**Row 2 — clarify, retain 4/5.** The watcher observes all selected role assignments and distinguishes peer waits, missing environments, human decisions and stalls. QA finding work is not automatically a human alert; notify only when the recorded continuation actually needs the operator or meets the stall rule. Dogfood's scheduled/off state and unused specialist capacity are not stalls. A human-held release/QA decision stays in attention even while intentionally HELD. No watchdog agent and no automatic wakeups.

**Row 7a — expand, retain 5/5.** The lead owns intake, role selection, Architect/Planner coordination, QA dispositions and Dogfood triage, while remaining the single user-facing authority. Its report says which promised outcomes were exercised and what remains unchecked—not merely that tests/review are green. Preserve lead pre-execution and current operator gates; no accidental implementation of deferred 7b.

**Rows 5/6a/X/C — retain ratings, extend coverage.** Record selected/omitted checks, exact tested candidate, QA findings, Dogfood usage evidence, ownership and dispositions on tickets; an omitted or blocked check is not PASS. Mechanical gates can require this structure, but do not decide whether the user outcome was satisfied. Recovery preserves the role assignment and candidate evidence; a reused pane must not silently inherit the previous role's authority.

**Order — add team design now, not more agents now.** Establish the responsibility/activation map before adopting YAML/cards, alongside the unchanged first infrastructure steps: `team design; 0 → 2 + 1a → P → 5 + 6a + X(ownership) → 3 + 4 + C + X(gates) → 1b`. P should include shared-seat lifecycle, independent QA and safe Dogfood scheduling, while remaining the agreed 60-minute evaluation—not an unbounded full-team trial. Separately authorized bounded role trials can use today's files/tickets and need not wait for custom infrastructure. Their evidence should determine later seat expansion. Nothing in this review launches such a trial.

Next discussion action: settle T1's activation/evidence rules and T2's eligible products first, then accept or revise the explicit lead-held Architect/PM contracts and optional Designer role. This changes the team's responsibilities without presuming that a larger permanent roster is better.
